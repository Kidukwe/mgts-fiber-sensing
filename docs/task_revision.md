# Переработка задач после ответа руководителя

Дата: 16 октября 2026. Основание: ответ руководителя, переданный пользователем,
и прямое указание пользователя переработать задачи без обязательной зоны 40 точек.

## Что нужно решить

Кейс требует Python-пайплайн цифровой обработки сенсорных данных и обученную
аналитическую модель для выделения паттернов. Практический сценарий — мониторинг
инженерных коммуникаций здания: кандидаты перегрева, охлаждения и локальных
температурных изменений, потенциально связанных с протечками.

Прогноз следующей температуры — вспомогательная обучаемая задача, с измеримым
числовым target. Продуктовый результат — проверяемая очередь событий: участок,
время начала/подтверждения, изменение, длительность, протяжённость и объяснение.
Физическая причина не размечена; автоматическое подтверждение протечки не заявляется.

## Подтверждённые исходные условия

- Сигнал в °C, точность ±0,1 °C.
- Пространственное разрешение 0,25 см.
- −300 — конец волоконной трассы; в признаках, target и рейтинге не участвует.
- Для времени без смещения используется фиксированный UTC+3.
- Размер, амплитуда, длительность рассматриваются совместно. Заданных границ
  аварии нет; статистические параметры и модель выбираются разработчиками.
- Привязки к комнатам, схемы трассы, меток происшествий и задержки получения
  полного профиля нет.

Пространственное разрешение не доказывает шаг хранения каждого файла: raw x имеет
различные численные шаги. Длины по индексам ×0,0025 м — явно указанное допущение.
Оно не используется для выдуманной привязки к зданию. Индексы и raw x всегда сохранены.

## Какие прежние ограничения сняты

40 точек, 53 зоны, первые 2120 точек, единственный файл 2.csv, горизонт только
120–121 секунд и интервалы UTC 00:00/14:12/19:12 были предложением PR #3/#5.
Они не являются требованиями преподавателя. Их нельзя использовать как критерий
«решение неправильное» после уточнения пользователя. Рабочая версия обрабатывает
шесть CSV, динамические длины и разные частоты измерения. Ширина агрегации задаётся
CLI; default 64 — инженерная опора, не норма и не размер предполагаемой аварии.
Соседние зоны объединяются в события с переменной протяжённостью.

## Как оценивать

Регрессия: для каждого файла 60/20/20 по времени целевого профиля. Train-only
калибровка признаков и scaler; варианты выбираются по validation. Доступную
прошлую историю разрешено использовать за границей split, как при последовательном
прогнозе. Между источниками история не переносится. Это осознанный действующий
протокол, а не прежняя схема с обязательным purge из PR #3.

Из-за отсутствия заданного горизонта используется следующий регулярный профиль.
Типичный интервал определяется по train; переходы вне 0,5–1,5 шага разрывают окна.
Test MAE/RMSE взвешиваются по времени, не числу зависимых зон. Отдельно показываются
ошибки разных зон и быстрых изменений. Test уже исследовался в первой версии;
повторная оценка v2 — сравнение на той же записи, не новый независимый benchmark.
Для подтверждения обобщения нужна новая отложенная запись или отдельный объект.

События: функциональная синтетика (нагрев, охлаждение, узкий пик, провал,
одиночный выброс, восстановление), отсутствие ложного объединения через gaps.
Синтетика использована при разработке и не заменяет внешние метки аварий.
Ни MAE прогноза, ни число кандидатов не являются precision/recall протечек.

## Роль типа объекта

Тип здания меняет расписания HVAC, нормальную температуру, теплопередачу,
контакт сенсора и трактовку причины. Одинаковая форма может быть штатным
включением отопления либо неисправностью. Поэтому численная детекция отделена
от гипотезы о причине; настройки под объект и паспортные абсолютные пределы
добавляются при появлении достоверных сведений, не выдумываются по CSV.
